# Queue engine

## Identifiers
| Identifier | Format | Generated by | Resets |
|---|---|---|---|
| Patient | `PT-######` | PostgreSQL sequence `patient_number_seq` | Never |
| Appointment | `APT-YYYYMMDD-####` | Per-day advisory lock (`DailyNumber`), using the booking date | Daily |
| Visit | `V-YYYYMMDD-####` | Per-day advisory lock, using the check-in date | Daily |
| Ticket | `PREFIX-###`, e.g. `C-001` | `queue_sequences` upsert (`INSERT … ON CONFLICT DO UPDATE … RETURNING`) | Daily, per service |

- All dates are the clinic's local operational date (`CLINIC_TIMEZONE`).
- Every identifier is generated atomically and backed by a unique constraint, plus a format `CHECK` where one applies.
- A ticket's number is stored as it was issued, so changing a service's prefix never rewrites history.

## Transitions
| From | Allowed to |
|---|---|
| `waiting` | `called`, `cancelled` |
| `called` | `serving`, `skipped`, `cancelled` |
| `skipped` | `waiting` (requeue), `cancelled` |
| `serving` | `completed`, `transferred` |

- **Recall** repeats the announcement for a called ticket. It is an event, not a status change, and is limited to `max_recalls` (proposed: 3).
- **Transfer** marks the serving ticket `transferred` and issues the next service's ticket on the same visit, in one transaction. The new ticket carries the clinical priority and `transferred_from_id`.
- Every transition, recall and priority change appends a `queue_events` row: previous and new status, actor, counter and remarks. A trigger rejects any update or delete of these rows.

## Call order
`App\Services\Queue\QueueOrdering` gives a stable, starvation-safe order:

1. **Clinical priority**: urgent, then high, then routine. Only nurses and doctors set it, for services in their departments, and a reason is required above routine. Scheduling never overrides clinical urgency. Emergencies follow the clinic's own protocol.
2. **Scheduling class**: appointment tickets come before walk-ins. A walk-in who has waited longer than `walk_in_safeguard_minutes` (proposed: 45) is promoted into the appointment class, so walk-ins cannot be passed over indefinitely.
3. **Eligibility time**: appointment tickets become eligible `early_eligibility_minutes` (proposed: 15) before their slot. They are offered only to the booked provider; any triage staff member can call the triage ticket for an appointment.
4. **Sequence number**, then id, as a deterministic tie-break.

**Requeue (proposed).** A requeued ticket keeps its number, priority and scheduling class. It becomes eligible again from the requeue time, so it rejoins behind those already waiting in its class.

## Concurrency and idempotency
- **Counter claim.** Call-next locks the counter row and requires the caller's open session at that counter. It refuses while a ticket is already at the counter.
- **Ticket claim.** The first eligible ticket is claimed with `FOR UPDATE SKIP LOCKED`, so concurrent counters never call the same patient.
- **Database guards.** Partial unique indexes allow one unresolved ticket per visit and service, and one called-or-serving ticket per counter. Each counter and each user can have at most one open session.
- **Idempotency.** Each submission from the workspace or queue board carries an idempotency key, stored in the event metadata under a unique index. A repeated request, such as a double click, returns the original result instead of acting twice.
- **Verification.** Multi-process tests (`tests/Concurrency`) race separate PHP processes against PostgreSQL to show there are no duplicate calls, numbers or transfers.

## Announcements and displays
- Changes are broadcast only after the transaction commits: `QueueTicketChanged` is followed by a queued `DisplayUpdated`.
- Broadcast types: called, recalled, started, skipped, completed, transferred, cancelled and requeued. Issuing a ticket and changing its priority are not broadcast.
- The payload is `{id, type, ticket, room, service_id, at}`. It contains no patient data.
- The spoken text names the ticket and room only, for example: "Ticket C, 0, 0, 1, please proceed to Room 1."
- Displays load an authoritative snapshot on start, on every reconnection and every 60 seconds. They ignore events at or below the snapshot's last event id, and any event already applied.
- Announcements play one at a time and are never repeated.
- A call made while a display was offline is shown after reconnection but not spoken late (proposed).

## Settings
The settings below are proposed defaults, adjustable under **Clinic settings**.

| Setting | Default |
|---|---|
| Early eligibility | 15 minutes |
| Late grace | 15 minutes |
| Walk-in safeguard | 45 minutes |
| Maximum recalls | 3 |
